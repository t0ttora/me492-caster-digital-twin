# Which navigation policy is worth testing on JANUS?

**Blind primary-source study · 27 November 2026**

**Replay GNM and ViNT first** on the same taught route to a photographed stopping position from which the dock QR is readable. GNM is the smallest deterministic baseline. ViNT is the first challenger because an independent indoor office-loop experiment recorded collisions in 1/10 ViNT trials and 5/10 GNM trials. Both had 0/3 in a simpler corridor. That is enough to test the difference on JANUS, too little to choose a controller for people-occupied space. [GNM paper][gnmp] · [ViNT paper][vintp] · [independent real-robot evaluation, Tables III–IV][ind]

**Use OmniVLA-Edge for the first language experiment.** It has a publicly listed checkpoint with explicit terms, a language-only input mode, an image-only mode for a matched comparison, and a published 6 Hz result on a Jetson Orin. Its released mask code needs a CPU portability check before that experiment. LeLaN is the more direct experiment for “go to the blue bin” and publishes a faster local action calculation, but its author-linked weights folder required Google sign-in in this review. For the fixed command “return to charger,” a local command-to-route lookup gives JANUS a language interface immediately. Compare learned language grounding on requests where changing the words should actually change the destination. [OmniVLA paper][omnip] · [Edge checkpoint][edgew] · [Orin measurement, Table I][asyncp] · [LeLaN paper, Table 2][lelanp] · [LeLaN release][lelanrepo]

**Keep final docking classical.** The learned policy may propose motion up to the QR staging area. None of the sources establishes JANUS CPU latency, peak memory, or successful docking. The evidence supports replaying frozen models before considering a GPU purchase or a training campaign.

## What the ranking measures

The only project input was the supplied description of a differential-drive robot with a passive caster, forward RGB, odometry and classical final docking. I searched public literature and release sites for monocular instruction following, language-conditioned object approach, image-goal navigation, visual teach-and-repeat, diffusion/flow navigation, cross-embodiment policies and edge/CPU measurements. I followed citations to the originating teams, inspected model/config/loader source and anonymously accessible file metadata, and sought real-robot evaluations by other groups. Only public primary sources support the findings below. This is a decision-oriented survey, with an evidence cutoff of 27 November 2026. No internal planning files or chats were consulted. I did not download weights, run inference or operate a robot.

Ranks are **test priority within a goal type**. In order, I considered whether JANUS can supply the inputs and use the output, whether a trained artifact is obtainable, how closely the demonstrated embodiment and task match, then the marginal compute, data and integration costs. Public file listings establish artifact identity and approximate size. Peak process memory, timing scope, and the right to redistribute weights each need separate evidence. A promised release, an available code license, or a simulator score cannot establish those properties.

## Image-goal navigation

A useful goal image shows **the scene as seen by JANUS at a navigable staging pose**. A cropped QR symbol or catalogue image removes much of the geometry these place-goal policies learned. For a dock behind two corners, record route keyframes through the corners and use the last safe approach view as the final node. The Berkeley reference implementation localizes against a window of keyframes and advances to a nearby visual subgoal. Its arrival flag tests the selected node index. It does not measure distance to the electrical contacts. ## Other models screened

- **LM-Nav** uses GPT-3 to extract landmarks, CLIP to associate them with nodes, and ViNG for visual control. It demonstrates why language-to-route selection is a sensible baseline. The published stack has a hosted language dependency. A deterministic station vocabulary is a smaller, entirely local baseline for JANUS’s designated destinations. [Original paper][lmnav]
- **Qwen-RobotNav** has a technically relevant eight-waypoint output and a reported 196 ms on Jetson Thor/Go2. Its authors explicitly say they have no current plan to release the weights. **Robostral Navigate** uses monocular RGB and language, trained on 2.4M simulated trajectories. Mistral describes image points/orientations and fallback relative displacements. I could verify a technical report, not an author-distributed runnable checkpoint and license. Both are inappropriate as the first offline experiment. [Qwen official repository][qwen] · [Mistral announcement][mistral] · [technical report][robop]
- **CoFL-S** has a downloadable checkpoint and demonstrated CPU loading. Its released input is **RGB-D** plus language, and its model license is limited to noncommercial academic research. **NavDP** likewise has a real pretrained RGB-D navigation implementation. **LiMo** uses just one RGB observation but asks for a metric robot-frame `x,y,yaw` goal. Reconstructing depth or converting an arbitrary goal photo to a metric pose would be additional JANUS subsystems. [CoFL-S release][cofl] · [NavDP official repository][navdp] · [LiMo official input format][limo]
- **MINav** is a relevant alternative if later collecting in-domain trajectories becomes affordable. Its “laptop” had an RTX 5070 and 32 GB RAM, and the physical experiments first collected in-domain experience. It answers a different resource question from frozen CPU replay. **Stock OpenVLA and SmolVLA** also require navigation-specific outputs and training evidence. The OmniVLA paper’s SmolVLA navigation number came from the authors’ adaptation. [MINav, `V-C][minav] · [OmniVLA baselines, `IV-C][omnip]

## Offline test plan for JANUS

Everything below is proposed. The first comparison needs one taught route, held-out traversals, the existing docking logs if available, and a CPU whose identity can be recorded. No training set is needed to establish whether running a frozen candidate is worthwhile.

1. **Define success before recording.** Pick a pre-dock staging region from which the existing classical controller has previously acquired the correct station. Record its envelope in metres and heading, camera mounting/FOV, expected QR ID and the actual controller’s validity/interlock signals. If that envelope or the robot footprint, velocity limits and braking behavior are unknown, mark their tests pending. The task for the policy is delivery to this envelope. Only the classical controller owns centering, final stop and the charge-enable decision.
2. **Make a small, leakage-resistant corpus.** A proposed first pass is one taught reference traversal per supported direction, two development traversals and at least two sealed traversals per route from different sessions. Add a second route or a visually similar non-station endpoint if available. Keep all frames from one traversal together. Reserve goal images from the teaching run, never a future frame from the held-out run. Log monotonic RGB capture times, exposure/resolution, odometry poses/timestamps and frame transforms, issued and measured velocities if available, QR detections/ID, interlock state, operator stops and interventions. Label first correct-QR acquisition, whether the scene permits forward motion, correct branch/landmark, and ambiguous intervals. Vary lighting and glare near the station, exposure changes at doorways, lateral/yaw offset and camera blur on turns. Record occluded or absent targets while stationary or under supervised teleoperation. Count independent traversals in the result, not just video frames.
3. **Use matched baselines.** Compare (A) zero-motion hold in stop/invalid cases, (B) route lookup plus odometric taught-path tracking, (C) nearest-keyframe appearance matching inside a bounded route window plus the same tracker, (D) GNM and ViNT with identical keyframes/controller, and (E) OmniVLA-Edge image-only and language-only on matched scenes. For language, include paraphrases, lookalike objects, left/right flips, unreachable or absent targets and prompts outside the supported vocabulary. Pair the **same observation** with two legitimate goals requiring different turns. Report both correct grounding and the fraction of requests on which the system can make a decision. A policy without an abstain output needs an external reject rule, calibrated on development data. Repeat with LeLaN only if the intended weights become accessible.
4. **Verify the adapter before scoring.** Use a read-only, network-disabled replay process with no motor or charging transport. For a future authorized run, pin code, weight revision/hash, exact config, encoder/tokenizer files, backend and precision, then require a complete parameter-key/shape audit. Match image channel order, normalization, crop/resize and history timestamps. Preserve each release’s reference cadence or explicitly resample; report missing frames. On synthetic straight, left, right, in-place and zero-motion fixtures check camera-to-base rotation, yaw sign, waypoint accumulation, units and timeout behavior. For the Berkeley policies the example scales XY by `max_v / frame_rate` and selects waypoint index 2. For OmniVLA-Edge the sample uses index 4 and 0.1 m spacing. Calibrate those conventions on development odometry. Treat a target’s lateral offset as curvature or turn-then-advance, with zero commanded lateral velocity. Reject non-finite values and infeasible commands. Passive-caster swivel, slip and swept footprint can matter even where a centerline fits. [Berkeley executor][navcode] · [velocity controller][pdcode] · [Edge decoder][edgerun]
5. **Score what replay observes.** Synchronize future odometry to each model’s horizon and transform it into the base frame at the RGB capture time. After applying the actual waypoint normalization, report mean and final displacement error in metres, heading error where defined, first-turn sign accuracy at labeled junctions, route-node error, incorrect advance and premature arrival count. Compare language target/branch accuracy on the paired goals and report failures by split. Treat deviation from a human trace as disagreement; more than one path may be valid. For sampled policies report a fixed-seed distribution and the performance of the actual selection rule. An oracle best sample is a separate diagnostic. Label clearances manually or against registered geometry if present. Odometry alone cannot label an unseen obstacle or certify collision-free driving.
6. **Profile the CPU end to end.** Record CPU model, RAM, OS/backend, thread count, precision, history, goal-window width and sample/solver settings. For each finalist record cold-load time, first prediction, incremental and absolute peak RSS, and p50/p95/p99 capture-to-accepted-proposal age, with preprocessing, route lookup and controller included. Use saved capture timestamps for simulated age and a monotonic wall clock for processing time. A proposed repeatable profile uses 20 warm-ups, at least 200 timed ticks, then one full route played at recorded speed with QR processing active. Report queue depth, drops and deadline misses. If converting or quantizing later, compare signed turns, waypoint/velocity errors and hold decisions to the frozen reference before interpreting its timing. A run that misses real time is still a valid offline comparator.
7. **Exercise handoff and decide.** Replay QR absent, wrong ID, first correct acquisition, QR lost, stale/frozen camera, stale odometry, two lookalike stations, a person crossing, and a caster reversal or tight turn. Check classic-controller ownership and stop priority at transitions. Inject a delayed learned command immediately after takeover and verify that it is discarded. Exercise stop and charge interlocks with recorded or simulated signals and electrically isolated outputs. Log every nonzero proposed and accepted command plus charging-authority transitions. Set a motion-age budget from measured braking and clearance, for example require `v × (observation age + actuation delay) + measured braking distance + uncertainty margin ≤ available clearance`. A missed deadline issues a hold. The replay screen requires **zero accepted learned motion after handoff, wrong-station handoffs or charge authorizations from model output**. To earn a later supervised trial, a model must also improve the predeclared route or language endpoint metric over the matched classical baseline on held-out traversals while meeting the host budget. Report raw counts and uncertainty by traversal; sparse data can leave the choice undecided.

Logged replay can reject bad geometry, wrong-goal steering, stale outputs and control-authority mistakes at recorded states. Once the proposed action diverges, the recorded camera continues along the operator’s path. Closed-loop route success, true stopping distance under load, caster response, physical clearance, QR reacquisition and successful charging remain unverified until measured on JANUS. If the classical route baseline already meets the staging requirement, the smallest defensible outcome is to retain it and use a learned model only for the language tasks where it demonstrates added value.
